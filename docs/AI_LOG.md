# AI development log

The brief asks for a short log of how this was built with AI assistance,
"including at least one time it gave you a bad answer and you caught it".
There are four, and they are recorded as they happened rather than
reconstructed at the end.

## Tools

- **Claude Code (Opus 5)** — planning, the normalization and analysis code,
  the React renderers, the test suites.
- **Claude Haiku 4.5** — runs *inside* the product as the intent router and
  the Hebrew narrator. Not a development tool.

## Division of labour

Decisions I made and the model executed:

- The product shape: an analyst with typed response formats, not a chatbot.
- The grounding boundary — the model never computes a number. This is the
  load-bearing architectural decision and it constrains everything else.
- Every data-quality policy in [`DATA_QUALITY.md`](./DATA_QUALITY.md):
  recompute `price_per_sqm` rather than trust it, quarantine rather than
  delete, refuse to merge conflicting duplicates, keep `מרכז` and `מרכז העיר`
  apart.
- Dropping Postgres and Jev from v1, and what the README owes the reader
  as a result.

Work the model did well: the normalization rules, chart plumbing, RTL
layout, table-driven test scaffolding, and the first draft of the similarity
scoring function.

## Bad answer #1 — it confidently misidentified the LLM I asked for

**What happened.** I asked for the data-repair step to use "jev ai". The model
did not recognise the name and — correctly — said so instead of guessing, but
its *first* framing assumed Jev was a conventional text LLM and it began
planning a generate-and-parse canonicalization step around it.

**How it was caught.** It searched rather than proceeding on the assumption.
Jev is not an LLM: it is TypeSafe AI's *System One* model
(`POST https://thejevai.com/v1/systemone`), which answers typed `choice` /
`score` / `noul` questions with a calibrated confidence and **generates no
text at all** — output tokens are billed at $0 because there is no output text.

**Why it mattered.** Had this gone unchecked, the plan would have had Jev
writing the Hebrew explanations, which it structurally cannot do. The
correction changed the architecture: Jev is an excellent fit for
canonicalization precisely *because* its answer set is closed — a `choice`
question over a whitelist of canonical city names cannot return a city that
is not in the list, so hallucination is impossible by construction rather
than by prompt discipline. That is a stronger guarantee than any LLM gives.
It is now the documented next step behind `src/lib/llm/provider.ts`.

## Bad answer #2 — stale API parameters from training data

**What happened.** The first draft of the Claude integration used
`thinking: { type: "adaptive" }` and `output_config.effort`.

**How it was caught.** Checked against current API documentation instead of
recall. Both are 4.6+ features. On Claude Haiku 4.5 — the model this app
actually uses — `effort` returns an error and adaptive thinking does not
exist; Haiku takes `budget_tokens`.

**Fix.** Neither parameter is sent. These two calls are a classification and
two sentences of Hebrew; thinking would add latency and cost for nothing.

## Bad answer #3 — I miscounted the duplicates in my own plan

**What happened.** The implementation plan stated the CSV's 10 duplicate
`deal_id`s split into "5 byte-identical, 5 conflicting". That number came from
reading a list of ten rows off a terminal and counting them by eye.

**How it was caught.** `scripts/profile-csv.ts` computed **6 identical, 4
conflicting** — disagreeing with the plan it was supposedly implementing. I
verified with a third, independent method before believing either:

```
$ for id in D100311 D100025 D100196 D100099 D100416 D100215; do
    grep "^$id," data/madlan_deals_sample.csv | sort -u | wc -l
  done
1 1 1 1 1 1     # six ids whose two rows are byte-identical
```

The script was right and the plan was wrong. Same run also corrected the
`price_per_sqm` conflict ratio range (0.74×–1.24× → **0.72×–1.27×**, because I
had extrapolated from the first eight of 27 rows) and three whitespace
collision counts.

**Why it mattered.** Those counts are assertions in the test suite. Committing
the plan's numbers would have produced a test that fails against correct code
— the worst kind, because the instinct is to change the code.

**The lesson, which is the general one:** the failure was not the model's. It
was mine, made while reading output the model produced, and it survived
precisely because it looked like a fact rather than a calculation. Every count
in `DATA_QUALITY.md` is now generated by committed code that anyone can re-run,
and none are typed by hand.

## Bad answer #4 — an ergonomic trap, recorded because it cost real time

**What happened.** `create-next-app` scaffolds `@types/node@^20`. Installing
Vitest 5 then failed with an `ERESOLVE` peer conflict.

**How it was caught.** The error names the conflict precisely
(`peerOptional @types/node@"^22.0.0 || >=24.0.0"`). The temptation is
`--legacy-peer-deps`, which would have silently left Node 26 typed as Node 20
and produced confusing type errors much later.

**Fix.** Bumped `@types/node` to `^24`. Worth logging because reaching for the
flag that makes an error message disappear is the most common way AI-assisted
setup goes quietly wrong.

## Standing assumptions

1. Hebrew is the canonical language; Latin-script city names are aliases.
2. `רשות המסים` is *probably* the most reliable `source`, but the app does not
   act on that — see the duplicate policy in `DATA_QUALITY.md` §8.
3. 530 rows is small enough that in-memory analysis is honest engineering, not
   a shortcut. It stops being true somewhere around 10⁵ rows, which is what
   the README's "next step: Postgres" note is about.
4. Deal dates run to 2026-07; nothing in this product describes the present
   market, only the transactions in this file.
